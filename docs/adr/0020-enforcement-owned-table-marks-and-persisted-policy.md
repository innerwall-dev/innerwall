# ADR-0020: Enforcement as one owned table replaced atomically, per-rule sets, connection marks for attribution, logged drops, simulation on the same chain, and policy that outlives the daemon

**Status:** Accepted

## Context

ADR-0003 fixed that the agent programs the host's native firewall, keeps every rule in one table it owns, and replaces that table as a unit. ADR-0011 fixed that the agent fails static, that the last acknowledged policy survives restarts and reboots, and that root on the host can always remove enforcement locally. ADR-0015 fixed the atomic apply-or-fail acknowledgement, and ADR-0018 shaped the agent's installed-policy boundary as an interface that takes each complete next policy, deferring disk persistence to the enforcement backend. ADR-0019 built the flow path that carries decisions to the control plane.

Implementing the Linux backend made a set of decisions concrete that none of those records fixed and that a later change could plausibly undo one at a time: how a rendered policy becomes a ruleset, how the ruleset is changed when only peers change, how an accepted connection is attributed to the rule that accepted it, how a dropped one is seen at all, what simulation installs, and what happens to the kernel's rules and the agent's knowledge of them when the daemon is not running.

## Decision

1. **One owned table, replaced in one transaction.** Every rule the agent installs lives in one `inet` table named for this system. A full apply is one `nft -f` script that declares the table (a no-op when it exists), deletes it, and recreates it with the new content; the script is one kernel transaction, so the host runs the previous ruleset or the new one and never a mixture, and a refused script leaves the previous ruleset in place, which is what lets the agent acknowledge `FAILED` and stay on its last good version (ADR-0015). No other table is read, written, or flushed. The one base chain hooks input at priority `filter + 10`: a host's own filter chains run first, an accept in one base chain never skips another, and a drop in either is final, so the agent adds constraints and removes none.

2. **One named set per resolved rule and address family.** Each rule's peers become elements of two interval sets, one per family, named from the resolved rule id with every character outside letters, digits, and underscore replaced by an underscore, so the authored rule id reads back from `nft list ruleset` alone. A change that is peer membership only, the high-churn quantity ADR-0015 made cheap on the wire, is applied as set element additions and deletions in one transaction, leaving every rule and every other set untouched; any other change is a full rendering. A set update the kernel refuses falls back to one full rendering before the apply is reported failed.

3. **Chain structure.** Accept loopback; accept established and related traffic; then one accept per rule and family, matching source in the rule's set and the rule's protocol and ports, setting the connection mark to the rule's index; then the terminal rule. The established-and-related accept comes before any rule and, with inbound-only scope (ADR-0010), is the invariant that makes it impossible for the agent to sever its own control-plane stream: that stream is an outbound connection the agent initiated, its return traffic is established, and nothing after that line can touch it.

4. **Attribution by connection mark; drops by log.** Rules in canonical order are numbered from one and each accept sets the connection's mark to its rule's number, so the mapping from mark to rule id is a pure function of the installed policy and the collector needs nothing else to attribute an accepted connection: a tracked connection carrying a rule's mark is `ALLOWED` by that rule. A dropped packet never becomes a tracked connection, so the terminal rule logs every packet it sees to a netlink log group before its verdict; the collector subscribes to that group and reports each logged packet as one attempt, `BLOCKED` under enforcement. The agent claims the connection mark on connections its rules accept; a host that already uses connection marks for something else is a coexistence question this version answers by documenting it, not by masking.

5. **Simulation is the same chain with one line changed.** Simulation renders exactly the enforced ruleset except the terminal rule, which logs, sets the reserved would-block mark, and accepts instead of dropping. Everything else, sets, marks, per-rule accepts, order, is identical, and a test asserts that the two renderings of one policy differ in exactly one line. A simulation verdict is therefore evidence about exactly the ruleset enforcement would install. Logged packets under simulation are `WOULD_BLOCK` attempts, counted the same way enforcement counts drops; the would-block mark lets the tracked connection contribute its bytes to the same record without counting it twice. Visibility mode installs the owned table with no chain: nothing is evaluated, nothing is logged, and collection continues from connection tracking as before.

6. **Rules outlive the daemon; policy persists to disk; only an explicit command removes either.** On every successful apply the canonical policy, with its version, is written atomically to the agent's state directory with mode 0600 under a magic line and a checksum. A daemon exit leaves the kernel rules in place. On start the daemon loads the file and re-applies it as a full rendering before it dials anything, so a reboot restores what the agent last acknowledged before the control plane is even reachable; the version it then reports in `Hello` is the persisted one, and the server still answers with a snapshot (ADR-0015). A file that fails its checksum loads nothing and is reported loudly; the kernel keeps whatever it holds until the next snapshot. Enforcement is removed only by `innerwall-agent down`, which deletes the owned table and nothing else, leaves the persisted policy on disk, and says exactly that: a daemon that is still running, or one that starts later, re-applies the policy. This closes the persistence deferral ADR-0018 recorded, and ADR-0018 is amended to say so.

## Consequences

- The kernel is the truth about enforcement and the persisted file is the truth about what the agent acknowledged; the two agree after every successful apply and after every start. A persistence failure after a successful kernel transaction is logged, not reported as a failed apply, because the acknowledgement describes the kernel.
- `nft list ruleset` is a complete debugging surface: set names carry rule ids, rule comments carry rule ids and marks, the terminal rule's comment names the mode.
- Blocked and would-block records count attempts, one per logged packet: a client that retries a refused connection is several attempts. Allowed records count tracked connections. The two are different quantities by construction and the schema keeps them apart by decision.
- The would-block mark and the rule marks occupy the connection mark. Another consumer of connection marks on the same host observes them; masking to a range is an additive change if a real host needs it.
- Simulation and enforcement share one rendering and one code path; a change to the chain structure changes both, and the one-line test says so.
- The local kill switch is honest about the trust model: it removes the kernel rules, it does not silence the daemon, and it says which of the two the operator has done.
- Every IPv4 and IPv6 rendering, delta, and persistence path is covered without privileges by golden and unit tests; the kernel-facing behavior (drops, attribution, simulation, set updates without reload, rules surviving the daemon, restart from disk, teardown) is covered by a network-namespace suite that runs as root in its own CI job and locally through `make test-netns`.
