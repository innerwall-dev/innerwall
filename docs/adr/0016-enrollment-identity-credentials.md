# ADR-0016: Enrollment, workload identity, and credential issuance

**Status:** Accepted

## Context

ADR-0004 fixed the identity model: token-gated enrollment with no trust-on-first-use window, a control-plane-assigned identity carried in a URI SAN, short-lived credentials, and a signing authority behind an interface. ADR-0015 then fixed the wire contract that carries it: a provisioning token scoped to a label set that may enroll many workloads, a certificate signing request on enrollment and renewal, and identity derived only from the connection credential.

Implementing both made three things concrete that ADR-0004 left open or stated differently, and each is the kind of detail a later change could quietly undo: the exact form of the identity URI, the exact rule for what a signing request may contribute to a certificate, and where on the listener the authentication boundary is enforced. This ADR restates the identity model in full with those decisions fixed, so that one record is the source of truth. Where ADR-0004 and this ADR differ, this ADR governs; everything in ADR-0004 not contradicted here is carried forward.

## Decision

1. **Signing goes through one interface, and a signing request contributes only its public key.** Certificate issuance is behind `ca.Authority`, whose two operations are `Sign(csr, identity, ttl)` and `Bundle()`. The interface belongs to the enrollment domain: enrollment and renewal are written against it and nothing outside a backend depends on how that backend keeps its key. Every implementation reads the request through one function that returns the public key and nothing else, after verifying the request's signature as proof of possession. The subject, every subject alternative name, and every extension the enrollee asked for are discarded, because identity is granted by the control plane and never requested by the enrollee. A test that submits a request naming another workload, the control plane's own hostname, a CA constraint, and arbitrary private extensions, and receives a certificate containing only what was granted, is the executable statement of this rule and stays in the repository for as long as the rule holds. Version 1 ships exactly one backend: a key and self-signed root on the control-plane host's disk, created by `innerwall ca init`, with the key file at mode 0600 and the directory at 0700. Backends that keep the key elsewhere are additive.

2. **Identity is one URI SAN of the form `innerwall://workload/<uuid>`.** An issued credential carries exactly one URI subject alternative name and no DNS, IP, or email names. The scheme names this system; the host component is a namespace (`workload`) rather than a network location, so that other kinds of principal can be named under the same scheme later without ambiguity; the path is the workload identity, a version 7 UUID assigned by the control plane at enrollment, in its canonical 36-character spelling and no other. A single package formats and parses this URI and extracts it from a certificate, refusing certificates with zero or more than one URI SAN; every other component uses that package and none builds or inspects the string itself. The common name mirrors the identity for human readers and is never read for authorization. Everything mutable about a workload (hostname, labels, enforcement state) lives in the registry, never in the credential: the certificate authenticates, the registry authorizes.

3. **Provisioning tokens are opaque, hashed at rest, scoped, expiring, revocable, and reusable within scope.** A token is the prefix `iw_` followed by 32 random bytes in URL-safe base64 without padding; the fixed prefix lets a secret scanner recognize a leaked token without knowing which deployment minted it. The control plane stores only the SHA-256 digest and shows the plaintext exactly once, at mint. A token carries the label set it assigns, an expiry (30 days unless the operator sets otherwise), and a revocation timestamp. It may enroll any number of workloads while valid, so one token can be baked into an image or a provisioning pipeline; a use is recorded, never consumed. A rejected token reports precisely why (malformed, unknown, expired, revoked), because the operator who minted it needs to know, and an attacker guessing values learns nothing from "unknown" they did not already know. Tokens are minted, listed, and revoked by the control-plane command line; a management API for them follows the API façade. "Provisioning token" is the wire contract's name for what earlier documents call a join token; they are the same object, and the constraints ADR-0004 placed on an enrollment policy are carried on the token itself in this version.

4. **Credentials are short-lived; renewal is load-bearing from the first version.** An issued workload credential lives 24 hours unless configured otherwise; the file-backed root lives ten years, because rotating a root means re-enrolling every workload while rotating a leaf costs one round trip. Renewal is the `RenewCredential` operation of the agent service: the workload being renewed is whatever identity the connection credential carries, the same URI SAN is reissued with a fresh serial, and the signing request is subject to the same rule as at enrollment. The agent exposes renewal as a command in this version; the daemon's automatic renewal at roughly half of lifetime follows with the daemon. A workload that misses its renewal window has no credential and re-enrolls with a new token. Validity begins a few minutes in the past so a host with a slow clock accepts a credential it was just issued.

5. **One listener, authentication decided per service.** The control plane serves the enrollment service and the agent service on a single TLS listener. The listener asks for a client certificate and verifies it against the authority bundle when one is presented, but does not require one at the transport layer, because the enrollment service is authenticated by the token and a workload that has not enrolled has no certificate to present. A server interceptor then enforces the boundary by service name: the enrollment service requires no client certificate; every other method on the listener requires a verified client certificate whose leaf carries a parseable workload identity, which the interceptor places in the request context. The default is to require a certificate, so a service added later cannot land on the unauthenticated side by omission. Handlers read identity from that context value and from nowhere else: not from request fields, not from the connection, not from a certificate they parse themselves.

6. **The bootstrap trust anchor travels with the token.** At enrollment the agent holds no credential and no bundle, so it has nothing of its own with which to verify the control plane. The operator therefore distributes the authority's certificate out of band together with the token, and the agent presents it as the trust anchor for that first connection. The token proves the agent to the control plane; the anchor proves the control plane to the agent. When the control plane presents a certificate the host already trusts, the anchor may be omitted and the host's trust store is used. After enrollment the agent stores the bundle it received and uses it for every later connection.

7. **The signing key is operator-provisioned configuration, not replica state.** The control plane keeps all durable state in Postgres so that replicas are stateless and interchangeable. A private signing key is the one thing that does not belong there: a key in the database is readable by everything that can read the database, and the point of a signing boundary is that it is not. The file-backed authority therefore holds its key on the host, and the authority directory is configuration the operator provisions identically on every replica, in the same class as the database connection string and the listener certificate (which `ca init` writes beside the key). Replicas configured identically remain interchangeable: every one signs with the same key and verifies against the same bundle. `ca init` is run once and its output distributed; `serve --init-ca` exists for a single-replica development stack and creates nothing when a directory already holds an authority. Nothing else durable lives on a replica, and a backend that keeps the key in a secrets manager or a hardware module removes even this from the host while leaving the interface unchanged. ADR-0017 restates the control-plane shape with this exception in it; this decision records the reasoning at the point of use.

## Consequences

- ADR-0004 is superseded. Its identity model survives in full; the URI form it named is replaced by the one above, and its token consumption rule is replaced by ADR-0015's reusable scoped token.
- ADR-0005 is superseded by ADR-0017 to carry decision 7: signing-key material is operator-provisioned on each replica rather than stored in Postgres. Two replicas that each generate their own authority are misconfigured, not two valid deployments; the deploy guide says so, and an external key backend removes the question.
- The signing-request rule is enforced in one function and tested by one hostile-request test. A backend that bypasses that function is a reviewable diff, not a subtle drift.
- The identity string has one owner. Changing its form is a change to one package and its round-trip tests, and every consumer follows.
- Token plaintext exists in exactly two places: the operator's terminal at mint and the agent's enrollment call. It is never stored and never logged, and the repository's tests check that a store lookup by plaintext finds nothing.
- Short lifetimes make renewal a hot path and the authority availability-critical for renewals. Enforcement is unaffected by either (ADR-0011). Revocation of a token stops future enrollments and nothing else; a deny-list of workload identities, for locking out an enrolled workload before its credential expires, is a registry feature that lands with the sync stream.
- Adding a method to the agent service requires nothing of the boundary; adding a service reachable without a credential requires a deliberate change to the interceptor's one exception, which is the review point.
- The bootstrap anchor is one more artifact for the installer to carry. Its absence in a development setting is a usability cost accepted so that a token is never sent to an unverified endpoint by default.

## Amendments

- **2026-09-13 (PR #5): relationship to ADR-0004.** This record implements ADR-0004's identity semantics at the signing boundary; it does not supersede ADR-0004. The `Supersedes: ADR-0004` header is removed, and the sentences in Context ("Where ADR-0004 and this ADR differ, this ADR governs") and Consequences ("ADR-0004 is superseded") are withdrawn. ADR-0004 remains Accepted.
- **2026-09-13 (PR #5): automatic renewal.** Decision 4 anticipated the daemon's renewal point as "roughly half of lifetime". The daemon renews automatically in the last third of the certificate's lifetime, at a jittered point, through the existing `RenewCredential` path, and swaps the renewed credential in without dropping its stream. A failed renewal retries with backoff; an expired credential is reported and the daemon does not enroll itself.
