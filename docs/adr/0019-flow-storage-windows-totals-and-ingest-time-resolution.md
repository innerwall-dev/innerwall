# ADR-0019: Flow storage as windows plus totals, peers resolved at ingest, bounded retention, and the query shapes the schema serves

**Status:** Accepted

## Context

ADR-0009 fixed that agents aggregate flows before shipping, that version 1 stores them in Postgres only, and that every read and write goes through a `FlowStore` interface over a column-shaped schema. ADR-0015 fixed the wire record: one `FlowRecord` per (source, destination, port, protocol, direction, decision) per reporting window, shipped on a telemetry stream of its own. Implementing the first end-to-end flow path, from the host's connection tracker to a queryable table, made four things concrete that neither record settled, and each is the kind of decision a later change could undo one plausible pull request at a time: what the rows are, when a source address is turned into a peer, how rows age out, and which queries the schema is shaped to answer.

The operator console's design produced the queries. It needs a workload's flows over a time range; a rollup over a label scope, filtered by decision and grouped by peer and service, to answer "what would this policy have blocked, and for whom"; and a "since first seen" verdict per flow key that does not depend on how much history is retained. A schema that served the first two by scanning and the third by scanning everything ever stored would be correct and slow in exactly the query that makes simulation trustworthy.

## Decision

1. **Two tables: windows and totals.** `flow_windows` holds one row per aggregated record per reporting window, as the agent shipped it plus what ingestion resolved. `flow_totals` holds one row per (workload, resolved peer, destination port, protocol, direction, decision), upserted in the same transaction as the window's rows: the counters add, the first-seen instant is the earliest, the last-seen the latest, and the label snapshot and matched rule are the latest window's. Windows serve time-bounded questions and are pruned; totals serve "since first seen" questions from one row and are never pruned. Both are column-shaped, with no nested structure beyond the label snapshot, so the same rows port to a columnar store behind the interface when an estate's volume demands it (ADR-0009). Both reserve `region_id` (ADR-0012). Beside them, `flow_gaps` holds the intervals in which a workload's agent knows its evidence is incomplete, one row per reported interval, keyed so that a repeated delivery is stored once; it is column-shaped, reserves `region_id`, takes the workload from the connection credential like the windows, and is read and written only through the same interface. A gap is not a flow record: it qualifies the windows of its workload over its interval, and nothing aggregates it into them. *(Amended 2026-10-04; see Amendments.)*

2. **Peers are resolved at ingest and stored with the row.** When a window arrives, each record's source address is resolved once, against the registry as it stands at that instant: a workload's current address wins, then the most specific address group containing the address, then nothing, in which case the address itself is the peer. A workload peer is stored with its identity and a snapshot of its labels at that moment. Resolution happens at ingest and not at query time because addresses are reassigned and labels change: a join at query time would show today's owner of an address as the peer of last week's flow, and today's labels as the scope it was in. The stored row is what the operator would have seen had they looked at the time. The reporting workload's identity comes from the connection credential and from nowhere in the payload (ADR-0016).

3. **Retention is a bounded, periodic delete of windows; totals are kept.** A scheduled job on every control-plane replica deletes windows that started before a configurable horizon (30 days by default), in bounded batches, each batch under a transaction-scoped advisory lock so that one replica prunes at a time and the others skip the round (ADR-0017). The job has a fixed period and runs whether or not there is anything to delete; nothing waits on it, so it is maintenance, not the polling ADR-0002 forbids. The same batches, under the same lock, delete gaps that ended before the horizon, so a gap is kept at least as long as any window it could describe. *(Amended 2026-10-04; see Amendments.)* Declarative time partitioning with retention by partition drop, which ADR-0009 named, is the recorded path when volume makes deletes expensive: the windows table is keyed by window start so the partition key is already in place, and the change is a migration behind the same interface. ADR-0009 is amended to say so.

4. **The schema serves three query shapes and the command line issues them first.** (a) A workload's windows in a time range, optionally filtered by decision, newest first. (b) A rollup over a set of workloads (a label scope, resolved by the caller to the workloads currently in it) in a time range, optionally filtered by decision, grouped by resolved peer and service (destination port and protocol), with the distinct workload count, summed counters, and the range of instants seen. (c) A workload's totals since first seen, optionally filtered by decision. The indexes exist for these and nothing else: (workload, window start) for (a), (decision, window start) for (b), window start for retention, and the totals primary key for (c). The `innerwall flows` commands issue exactly these queries, so the storage shape is proven by the only read surface that exists before the API façade (ADR-0007) lands. The operator surface's read model adds five named groupings of shape (b) over the same windows and indexes, each its own statement (by matched rule, with the distinct workload count; by rule and resolved peer; by resolved peer and reporting workload; by reporting workload and service; by resolved peer and service, with the distinct workload count, which is (b) itself), bounded to a documented number of groups with the totals of the whole, and a form of (a) paged by a cursor on (window start, row id); there is no free-form grouping. The evidence gaps have one read of their own, not a grouping: the gaps of a workload set (one workload, a label scope resolved as for (b), or every workload) that intersect a half-open range, newest first and bounded, as one named statement served by a (workload, gap end) index, with gap end also serving retention. *(Amended 2026-09-13, 2026-09-28, and 2026-10-04 twice; see Amendments.)*

5. **The agent's side of the pipeline is bounded and independent of the sync stream.** The collector aggregates observations from the host's connection tracker on the wire record's key over the window the control plane configures in `SyncConfig`; a closed window enters a buffer bounded in records; when a window does not fit, the oldest windows are dropped first and every dropped record is counted into the heartbeat's `dropped_flow_records`, so the operator knows the map is incomplete before trusting it (ADR-0011). Each drop is also an evidence gap over the dropped window's bounds with the count dropped, beside the gaps the sources record (a kernel overrun, a restart, a table dump cut at its bound); the reporter ships the gaps held with the next window and puts them back when its stream fails. *(Amended 2026-10-04; see Amendments.)* The reporter ships one window per `ReportFlows` stream, in requests capped at `SyncConfig.flow_batch_max_records`, over a connection of its own with its own jittered backoff, so telemetry never shares the sync stream's fate (ADR-0015). Records that fail validation at ingest are skipped and counted; the rest of the window lands.

## Consequences

- A flow record is immutable history: the peer it names and the labels it carries are the ones in force when it was observed. Renaming, relabeling, or re-addressing a workload changes nothing already stored. A display that wants the peer's current name looks it up by the stored identity; the snapshot is for the scope the flow was in.
- "Since first seen" is one row per key regardless of the retention horizon, at the cost of one upsert per key per window, which the batch write makes cheap.
- Retention is a delete, not a partition drop, in this version. It is bounded and serialized, and it is the first thing to revisit when window volume makes it visible. The migration to partitioning changes nothing above the `FlowStore` interface.
- The rollup resolves its label scope at query time, deliberately: it answers what the workloads in scope now have seen. The stored label snapshot answers the other question, what scope a flow was in when it happened, and the two are not conflated.
- The buffer is in memory and bounded in records. Buffering to local disk across an agent restart, which ADR-0011 anticipates, is additive behind the same buffer and lands with the resource budgets it belongs to.
- Byte counts depend on the kernel's per-connection accounting being enabled; where it is off, connections are counted and bytes are zero, and the agent says so once at start. The agent does not change kernel settings on the host's behalf.

## Amendments

- **2026-09-13 (PR #10, M3.2 operator read model).** Decision 4 gains the groupings the operator surface's rollup endpoint serves and the cursor-paged form of the windows list, as additive detail: four named groupings over the same windows and the same indexes, each one hand-written statement chosen by name, never assembled; a rollup bounded to a documented group cap that returns the top groups in its order with the totals and group count of the whole and a marker when truncated; and pages keyed by (window start, row id) so a window landing between pages neither repeats nor hides a row. The peer in every read is the one stored at ingest (decision 2); the read model looks up only the current display name of the stored identity. No schema or index changes; the core decision stands.
- **2026-09-28 (PR #17, M3.7 simulation review).** Decision 4's operator-surface groupings gain a fifth, by resolved peer and service with the distinct workload count per group: the shape (b) already names, served on the rollup endpoint as `group_by=peer,service` with `workload_count` on each group, as its own named statement over the same windows and indexes. The simulation review's rows, matrix, and recency ordering are keyed by peer and service; the four groupings could produce them only by assembling rows client-side, which ADR-0007 as amended rules out. Additive detail; no schema or index changes; the core decision stands.
- **2026-10-04 (PR #19, M3.8 policy editor).** Decision 4's grouping by matched rule gains the distinct workload count per group, `workload_count` on the rollup endpoint, in the shape the fifth grouping carries it: the policy editor states each rule's hit counters with the number of workloads in scope that reported them, and no grouping could give that number without assembling it client-side, which ADR-0007 as amended rules out. The same statement over the same windows and indexes gains one aggregate; the set of groupings stays closed at five. Additive detail; no schema or index changes; the core decision stands.
- **2026-10-04 (PR #22, flow-collection gaps).** Evidence gaps join the schema, the pipeline, and the reads, as additive detail. Decision 1 gains `flow_gaps` beside the windows and totals: intervals in which a workload's evidence is known to be incomplete, stored once per reported interval, with `region_id` reserved and the workload taken from the credential. Decision 3's retention deletes gaps that ended before the horizon in the same locked batches, so gaps outlive every window they describe. Decision 4 gains the gaps read, one named statement over a workload set and a half-open range, which is not a grouping; the set of groupings stays closed at five. Decision 5's buffer records every drop as a gap as well as counting it, so the one loss model covers the buffer and the sources alike. A range whose evidence has a gap in it is not complete evidence, and the readers that draw a verdict from flows say so (ADR-0001). The windows and totals, their indexes, and the core decision stand.
