## Screen-to-endpoint mapping

Every read is scoped by the ruleset's own selector, passed as repeated `label` requirements. Those resolve through `policy.MatchWorkloads`, the renderer's scope match. The range is one fixed `from`/`to` for every read.

### Header, tabs, scope (01–06)

| Element | Supplied by |
|---|---|
| Ruleset tabs | `GET /rulesets`, enabled only. A disabled ruleset renders nothing, so there is nothing of it to review. |
| Per-ruleset `◆ N` on tabs | `GET /flows/rollup?group_by=peer,service&verdict=would_block&label=…` for each enabled ruleset, folded into rows the way the table folds them. "+" when truncated. |
| Default ruleset | The one with the most would-block pairs; ties go to listing order. Named into the address (`?ruleset=`), so the breadcrumb names it. It is not read twice. |
| Scope line `app=checkout AND env=prod` | `ruleset.scope`; a key with several values is printed as `(k=a OR k=b)` |
| "42 workloads in scope · 40 simulation · 2 visibility · 1 degraded" | `GET /workloads?label=…`, walked to the end; `mode`, `sync.state`, `applied_version` vs `latest_version` |
| Edit ruleset | Inert, like "Open in policy editor" (M3.6 ruling): the editor is not built |
| Promote to enforced… | Opens the dialog; primary style when the verdict is safe, secondary otherwise (design) |

## Decisions made in session, open to review

1. **The E2 premise, corrected.** With `workload_ids`, a workload deleted between preview and submit comes back as a **400 `validation`** finding on `workload_ids[i]` (`fleet.ErrUnknownWorkload`), not a 409. A relabel doesn't move an id set at all. As ruled, the 409 renderer and its test stay; it covers the documented contract, reachable, for example, by a resubmission that resolves differently. The realistic stale-preview case, the 400, is rendered with the same "Preview again" path, and is tested too.
2. **Workload peers fold by their full label set**, with the workload count exact where it can be established and "N+" otherwise (see the Workloads row). This is the M3.6 folding precedent (ADR-0008 label groups), extended to the key that policy itself cannot split. The only extra reads are the `src,dst` rollup per decision, two fixed requests, not a per-service fan-out.
3. **The rule for allowed rows is named in the drawer**, not in the table's Rule column: `peer,service` carries no rule, and a `rule,peer` read per row happens only when the row is opened.
4. **Acknowledgment when not safe but nothing would be dropped** (sync or visibility conditions only): "I understand this scope is not safe to enforce yet". The approved wording counts pairs, and here there are none.
5. **Opt-in for unsynced workloads** covers pending and offline simulating workloads as well as degraded ones, each with its own reason: "has applied only vN", or "takes the change when it reconnects".
6. **Two banner states the design has no shot of:**
   - An empty scope: "No workload in scope".
   - An all-enforced scope: "Nothing is simulating in this scope".

   Neither can read as safe.
7. **Only the would-block and allowed decisions are shown.** Visibility workloads only observe (stated in the caveat), and enforced workloads already block.
