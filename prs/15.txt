The spec disagreed with the server on two of three names (`group` vs `address_group`, `address` vs `unknown`) and used `unknown` for the wrong case. This PR adds no database constraint. `ui/src/api/generated.ts` is regenerated.

## 2. Ack and apply-failure instants

The store held the failure detail and the applied version but no time for either event. `last_seen_at` moves on every message, so it can't stand in. So:

- **Migration `00007`:** adds `workloads.last_acked_at` and `workloads.last_apply_failed_at`, not backfilled.
- **Where they're stamped:** where the sync path already records the ack.
  - An APPLIED ack stamps `last_acked_at` through `RecordApplied`.
  - A FAILED ack goes through the new `registry.Store.RecordApplyFailed`, which records the degraded state, the agent's detail, and `last_apply_failed_at` together (it replaces the `SetSyncState(DEGRADED, …)` call).
  - The version a Hello claims is not an ack and stamps nothing.
- **After recovery:** a later successful apply clears the detail and keeps the failure time. The sync state says whether the failure still stands.
- **Where they're read:** the workload read's `sync` object gains `last_acked_at` and `last_apply_failed_at`. Both are always present and null when nothing is recorded, the same required-but-nullable pattern as `last_snapshot_sent_at`. `innerwall workload status` prints them.
- **Seed:** the dev seed's degraded workload now goes through `RecordApplyFailed`, so it carries a failure time.

## Item 3: dropped as already implemented

innerwall-dev/innerwall#14's gap note ("the surface holds `expires_at` only") was wrong. A successful renewal already stamps `last_renewed_at` (`enroll.Service.Renew` → `Store.RecordRenewal` → `RecordWorkloadRenewal`). The workload read already returns it as `health.credential.last_renewed_at`, and it is in the spec and `generated.ts`.

Per the ruling, the "renews in" display is presentation. The console derives it as issued time + two-thirds of the credential lifetime, the renewal rule recorded in ADR-0016 decision 4 and its 2026-09-13 amendment; the agent's jitter is acknowledged and not modelled. That is carried to the next console session. The declined options were a server-computed renewal time and an agent-reported one: the server does not model agent scheduling, and the agent contract does not change in M3.

## 4. Advertised gateway address

- **Setting:** `serve --gateway-advertise-address` (or `INNERWALL_GATEWAY_ADVERTISE_ADDRESS`) takes a `host:port`, the form the agent's `--server` takes. Any other value stops startup with an error.
- **No guessing:** the address is never derived from `--listen` or the host's interfaces.
- **On `/me`:** `GET /api/v1/me` carries it as `gateway_address` beside `site`, null when unconfigured, so the console keeps its placeholder. The login reply shares the `Me` shape and carries it too.
- **Handler:** the handler stays a pass-through of configuration, the same as `site`.
- **Not done:** `docker-compose.yml` is not configured with a value. Setting one there is a small follow-up if the dev stack should show a real address.
